# Certification states and their owners

| Level | Current decision | Evidence and scope |
|---|---|---|
| Numerical witness | Matched | The independent inputs and controlled three-mode comparison establish the named sample and discriminate the mode at that epoch. |
| Receipt consistency | Consistent Swiss file for Luna’s sample | The frontend checks each identity/time, library, contract, flags, policy and file fields, and validates the declared derived graph. The same surface can describe permitted fallback and mixed providers. |
| Sample provenance | Incomplete | The backend describes index rules, vectors and projections. A declaration of the dependency graph alone does not bind the numerical result to the values that produced it. Bind actual contributing values/receipt identities or replay the derivations from the same bound sample. |
| Runtime assurance | Incomplete | The phase path has a request snapshot and protected batch. The current route and helper traces found two state-dependent conversion sites outside ownership and a strict-strength calculation group with ambient path selection. |
| Native presentation | Numerical restart observed, incomplete provenance correctly displayed | Two sidecar sessions, identical exact selection and displayed numbers. The manifest lists both outstanding reasons. |

**Duplicated status gates.** In backend/phase_provenance_assessment.py, assess_phase_sample seeds both reasons unconditionally and returns incomplete for every valid result. In backend/avg_all_currency_phase.py the enclosing status and derived binding status are fixed to partial/incomplete. In src/avgAllCurrencyPhase.ts, avgAllProvenanceStatus also unconditionally returns incomplete for valid samples. These defaults accurately express today's state, but closing the runtime work alone cannot produce a positive label. Have one backend decision consume the build-scoped ownership result and transaction-specific inputs. Keep the frontend’s independent structural check as a fail-closed consumer. A frontend, backend and native reimplementation of the same astronomical proof is redundant.

**Differences to resolve before a positive state.** The backend accepts a JPL provider bit in its structural provider check. The frontend admits only Swiss and permitted Moshier. The backend accepts an empty string as the path with a valid-looking hash; the frontend requires a nonempty path. Both need a regression for contradictory returned coordinate bits. Treat unexpected JPL or a profile mismatch as incomplete for this phase contract. The same fixtures must yield the same policy conclusion at both boundaries. The frontend’s positive mixed-provider consistency result does not entitle a sample to a Swiss-only badge. Keep mixed output explicitly described and incomplete unless every contribution is bound under an expressly supported mixed policy.

Ownership is a build/process property. The per-sample assessment may reference that evidence. It must also verify all 10+7+7 inputs for the selected epochs and bind them to the derived geometry. These are different prerequisites that can share the same execution evidence. Native restart is already satisfied for the recorded sample. A positive native provenance claim would require a positive certified sample actually presented by that consumer; the two archived runs intentionally displayed incomplete. Native rendering is not a prerequisite to establish backend lock ownership.
